## 5. 架构方向：接口 + 模块

**目标形态**：宿主只认 `manifest`，不认代码。增删模块不改宿主。

```
modules/<name>/
  manifest.json    { name, version, kind, entry, ports[], health, configSchema, events, permissions }
  index.mjs        // 只导出 start/stop/health/handle
  README.md
```

- `kind`：`service`（常驻，要有端口）/ `tool`（被调用）/ `adapter`（对外连通：QQ、企微、DSH）/ `plugin`（宿主侧 UI 扩展）。
- 统一约定：**健康探针 `health()` 返回 `{ok, detail}`；启动必须报 pid + 端口；停止必须幂等**。
- 宿主统一负责：启动顺序、重启退避、健康汇总、配置校验、端口占用检查——**现在这些散在 supervisor.ps1 / watchdog.ps1 / start.bat / bridge 自己里，正是重复劳动的大头**。

**建议的六个一等模块**（从今天的资产直接切）
1. `inbound`：OneBot 事件 → 标准化消息（含媒体、转发、引用）
2. `wake`：唤醒判定（概率/@/关键词/观察窗）
3. `outbound`：发送（群/私聊/表情/语音/引用）＋送达确认＋重投
4. `store`：落盘、历史检索、记忆（唯一写入口）
5. `console`：控制台 API（现在的 `/api/*` 一大片）
6. `adapters`：`qq`、`wecom`、`dsh` 三个 adapter 各自独立

**迁移顺序**（每步都能单独上线、能回滚）
① 先加 manifest + health + 端口自检（不改行为）→ ② 把 `console` 抽出去（`/api/*` 全部改由 console 模块注册）→ ③ `outbound` 抽出（它现在是最痛：送达确认/重投混在 bridge）→ ④ `wake` 抽出 → ⑤ `inbound`/`store`。
