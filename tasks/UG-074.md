## 接口契约

**新增一个只追加的日志文件（这是本单的"接口"）**：

```
logs\archive.jsonl        每行一条 JSON，UTF-8 无 BOM，追加写，永不改写旧行

必须字段：
  t        : number   毫秒时间戳
  op       : "archive" | "pending-archive" | "force" | "skipped-already-archived"
  by       : string   谁触发（"00" / "rotate:worker=演练" / "manual:01" / "pending"）
  sessionId: string   被归档的 DSH 会话 id（全 id，不截断）
  title    : string   归档前的会话标题（可为空串）
  before   : number   归档前 archivedSessionIds.length
  after    : number   归档后 archivedSessionIds.length
  ok       : boolean
  error    : string?  失败时的原因（ok=false 时必填）
```

**不变的部分**：`handoff.mjs` 的既有 CLI 参数、`state\handoff.json` 结构与语义、归档本身的实现（只加一行日志，不改归档行为）。

## 0.5 预期结果

以后再有人问"归档集合为什么从 95 涨到 256"，`logs\archive.jsonl` 里能查到**每一条是谁、什么时候、归了哪个会话**。

## 1. 做什么

在 `scripts\handoff.mjs` 的归档成功/失败两条路径上**各 append 一行**到 `logs\archive.jsonl`（字段见接口契约），覆盖 `--pending`、单会话归档、`--force` 三种入口；写日志失败**不得影响归档本身**（try/catch 包住）。

## 2. 预期结果

- `logs\archive.jsonl` 存在，且每做一次归档就多一行；
- `before`/`after` 与 `workspace.json` 的 `archivedSessionIds.length` 对得上（差值为 1，幂等跳过时为 0）；
- 失败也有记录（`ok:false` + `error`）。

## 3. 验收与判据

- ① **成功路径**：对一个可归档的会话（可用那 10 个「鲟鱼—演练」之一，先与 01 确认）跑一次归档，`logs\archive.jsonl` 新增 1 行，字段齐全（贴该行原文 + `before/after` 数值）；
- ② **幂等路径**：对**已归档**的会话再跑一次，**不重复归档**且日志记 `op:"skipped-already-archived"`（贴行）；
- ③ **反例（必须做）**：传一个不存在的会话 id → 归档失败，日志仍新增一行 `ok:false` 且 `error` 非空（贴行）；
- ④ **不影响主流程**：把 `logs\` 临时设为只读（或用一个不可写路径）跑一次归档，**归档本身仍然成功**（日志写失败只打 warn）。

## 4. 边界

- 只改 `scripts\handoff.mjs`（+ 必要的日志小工具）；**不新增 npm 依赖**；
- **不改** `workspace.json` 的读写路径、不改归档语义、不改 `state\handoff.json` 结构；
- **不动** `logs\rotate.jsonl`（那是另一套）；不要顺手"修"UG-075（`--pending` 按 id 校验）——那单单独做，但本单日志字段要能表达它的 `skipped-already-archived`；
- 不删任何现有日志文件；要协调找 01。
