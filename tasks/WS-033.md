# WS-033 · QQ 桥的性能病根（每小时卡一次，工作台显示"断开"）

> 建单 2026-11-08 01:55｜目标 **02（插件）**｜项目 avatar / feature win-shell
> 现状：桥端口在听，但 HTTP 首次请求 **2.6–4.6 秒**，偶尔直接挂死；工作台/自检因此判它"断开"。

## 一、三个病根（本体已实测定位）

**① `/api/status` 每次现算，冷启动 2.6–4.6 秒**
- 扫描 **564 个会话** + 读多个大文件；
- 结果：自检/工作台 1.3s（已放宽到 12s）也可能超时；桥看起来"时好时坏"。

**② `token-usage.jsonl` 每轮整文件重写**
- 主文件 **4.1 MB**，还留了 **100 个 4 MB 级 `.tmp` 残片**（共 417 MB）；
- 每次重写 = 写 4 MB + 改名，**事件循环被占住**，HTTP 就挂。

**③ `投递失败.jsonl` 只增不减**
- 单文件 **24 MB / 25,938 行**，且**每次投递都要读它**；
- 已由本体手工把这两个大文件轮转到 2000 行（备份 `.bak-<时间>`），**但代码层面没修，会长回去**。

**旁证**：桥被两次强制重启，重启前 CPU 累计 4,516 秒 / 2,475 秒，HTTP 8–10 秒无响应。

## 接口契约（不改对外行为，只加缓存与上限）

```
GET /api/status
  → 行为不变，但内部加 3 秒缓存（同一秒内多次请求复用同一份）；
    缓存命中时返回 { ..., cached:true, builtAt }
  → 冷启动预算 < 1.5s（会话数 600 内）

写 token-usage：
  → **append-only**（一行一条）；**不再整文件重写**
  → 单文件 > 8 MB 时自动轮转 token-usage.1.jsonl（保留 2 代）

写 投递失败：
  → 单文件 > 5 MB 时轮转；**读取时只读最近 2000 行**（别整文件 parse）
```

## 0.5 预期结果

**桥冷启动后的第一次 `/api/status` < 1.5 秒，之后 < 50 毫秒**；**连续跑 1 小时不再挂死**；`token-usage.jsonl` 不再出现 `.tmp` 残片；`投递失败.jsonl` 不超过 5 MB。

## 1. 做什么

1. `/api/status` 结果缓存 3 秒（含 `builtAt`）；
2. `token-usage` 写入改 **append**（找出现有重写点，改掉）；
3. `投递失败` 读取改 **读尾部**（`fs.readSync` 从末尾读，命中即停）；
4. 两个文件加**大小上限 + 轮转**（保留 2 代）；
5. **加一条自愈**：启动时若发现 `.tmp` 残片 > 50 个，清理超过 10 分钟的。

## 2. 可验方式

- ① 重启桥后立刻 `curl /api/status`：**首次 < 1.5s**、第二次 **< 50ms**（贴 curl 的 `%{time_total}` 两次）；
- ② 连续采样 10 次（每 5 秒），**全部 200 且 < 200ms**（贴）；
- ③ 跑 1 小时后 `token-usage.jsonl` **无新增 .tmp**（贴目录列）；
- ④ `投递失败.jsonl` 超过 5 MB 会自动轮转（贴文件名变化）；
- ⑤ 工作台 `/api/console/selftest` 的 `qq-bridge` 项**连续 3 次全绿**（贴）。

## 3. 边界

- **不改桥对外接口的字段**（只加 `cached/builtAt`）；
- **不动消息收发逻辑**（只动状态查询与记账）；
- **不删历史账**（轮转，不删除）。

## 4. 回滚

`src\bridge.js.bak-ws033`；轮转策略有开关（`config.json` 的 `storage.rotateMB`，默认 8）。

## 5. 附加要求

- **改完必须压测**：模拟 20 次并发 `/api/status`，全部 < 500ms；
- 交付贴真实数字，不许只说"优化了"。
