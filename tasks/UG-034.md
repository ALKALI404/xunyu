## 0.5 预期结果

1. **`impl` 类任务**：没有「接口契约」小节 + `contract` 字段 → **派不出去**（`409 no-contract`）；
2. **`impl` 类交付**：没有分「接口 / 模块 / 证据」三段 → **预检门 FAIL**；
3. **诊断**：`node scripts\diag.mjs --feature <id>` 先跑接口探针、再跑模块用例，**直接告诉你坏在哪一层**。

## 1. 做什么

### A. 任务书闸门（`check-task-book`）
- 票标记为 `impl`（新增 `--kind impl`，默认 `impl`）时，任务书**必须**含：
  `## 接口契约`（至少：输入/输出 schema 或函数签名或 HTTP 路由）+ 项目栏 feature 的 `contract` 非空；
- 缺任一 → `dispatch` 拒（`409 no-contract`），提示"先写接口"。

### B. 交付闸门（`delivery-check.mjs`）
- `impl` 交付必须有三段小标题（顺序也要对）：
  `接口（定义/变更/版本）` → `模块（实现落点）` → `证据（怎么验的）`；
- 接口段里**没写"变更了什么接口"或"接口未变"**→ FAIL；
- 允许"接口未变"这一句，但**必须显式写**。

### C. 诊断器（新增 `scripts\diag.mjs`）
```
node scripts\diag.mjs --feature auto-exe
  → 1) 接口层：contract 里的端点/函数存在？schema 匹配？(探针)
  → 2) 模块层：功能用例跑不跑得过？(用例)
  → 3) 结论：{layer: interface|module|ok, cause, fix}
```
- 接口不过 → **不跑模块**（避免在错的基层上瞎调）；
- 输出必须含**"问题出在哪、怎么解决"**两行。

## 2. 预期结果

- 造一张无 `## 接口契约` 的 impl 任务书 → 派发被拒；
- 造一份无"接口"段的 impl 交付 → 预检 FAIL；
- `diag --feature` 对一个真断掉的 feature，能指出是接口层还是模块层。

## 3. 验收与判据

- ① 无接口契约被拒（贴 409）；
- ② 无接口段交付 FAIL（贴）；
- ③ `diag` 输出含 layer/cause/fix 三字段（贴两条：一条接口坏、一条模块坏）；
- ④ 接口坏时**不跑模块**（贴日志顺序）。

## 4. 边界

- 改 `check-task-book`、`delivery-check.mjs`、`worklist.mjs`（--kind）；新增 `diag.mjs`；
- 不改状态机、不改已有票的状态。

## 5. 回滚
