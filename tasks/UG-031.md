## 0.5 预期结果

`state\priority-list.json` 有内容时：**只派名单内、依赖已清的叶子票**；名单外 `dispatch`/`claim` 一律 409 `out-of-priority`；名单全 done 后**自动回落**到"谁闲着谁开工"。

## 接口契约

- `evaluatePriority(ticket) -> {ok, code}`：名单外返 `{ok:false, code:"out-of-priority"}`。
- `pickNextByOwner(owner) -> ticket|null`：priority 升序 → 依赖已清 → owner 空闲。

## 1. 做什么

1. 读 `state\priority-list.json`（支持 `单号` / `project:xxx` / `feature:xxx`）；
2. **计算可派集合**：名单内的票 → 取依赖（`blockedBy`/`dep`）已全清者；
3. **三处拦截**：`dispatch`、`claim`、`autoRelay` 全部走同一判定函数 `evaluatePriority(ticket)`；
4. **解锁推进**：任何票 `done` 后立刻重算，派新解锁的叶子票给空闲工号；
5. **回落**：名单内全 done/drop → `active:false`，恢复旧规则；
6. **成环/悬空依赖** → 报错并停止派发（不许瞎派）；
7. 同一判定函数也用于 `GET /api/priority`（可观测）。

## 2. 预期结果

造 A→B→C 依赖链 + 名单外 D：只能派 A → A done 派 B → B done 派 C；D 三次都被拒；C done 后 D 可派。

## 3. 验收与判据

- ① 依赖链推进日志（三次 dispatch，贴 ticket）；
- ② 名单外 D 的 `dispatch` 与 `claim` 都被拒（贴两条 409）；
- ③ 名单清空后 D 可派（贴成功）；
- ④ 成环用例被拒并报错（贴）。

## 4. 边界

- 不改状态机、不改负载闸规则（两者叠加生效）。

## 5. 回滚
