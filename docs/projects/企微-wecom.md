## 1. 定位

企微官方要求：应用回调必须是**备案域名 + 固定出口 IP + https**。家里是动态 IP、也没有公网入口，所以本项目的核心不是业务，而是**把不可达变成可达**：

- 收：`https://theglobalscm.top/wecom` → 服务器 nginx → SSH 反向隧道 → 本机 8788 服务；
- 发：官方**没有**会话式发送 API → 用**代持账号 + 客户端界面自动化**（Win32）把消息发出去；
- 群的限制先说死：应用回调**只覆盖应用单聊**；群与外部联系人聊天要拿全量消息，只能走「会话内容存档」（**客户付费，约 900 元/年**）。

**不是**：不是客服工作台、不做营销群发、不替代企微官方通道。

## 2. 边界

- **属于我**：企微回调服务（本机 8788，`E:\DSH-WeCom\bridge\src\server.mjs`）、服务器侧 nginx 443 与 `/wecom` location、SSH 反向隧道（服务器 `127.0.0.1:18788` → 本机 `8788`）、隧道 keeper（30s 探针 + 自愈）、代持发送（CLI/runner）、`logs\wecom-tunnel.log`、`E:\DSH-WeCom\bridge\config.json`（凭据不落 git）。
- **不碰**：客服工作台的页面与业务（`wecom-cs`）、各平台接入（P2）、企微后台配置（主人/甲方操作）。

## 3. 架构

```
企业微信（甲方/我方后台）
   │  HTTPS 回调
   ▼
https://theglobalscm.top/wecom
   │  nginx 1.24（Ubuntu，115.191.6.89）location /wecom
   ▼
127.0.0.1:18788（服务器侧隧道口）
   │  SSH 反向隧道  ssh -N -R 127.0.0.1:18788:127.0.0.1:8788 root@115.191.6.89
   ▼
本机 127.0.0.1:8788（DSH-WeCom bridge，受 watchdog 托管）

侧路：本机 keeper（每 30s 探针 https://theglobalscm.top/wecom）→ 判死 → 杀残留 → 重起隧道
发送：工作台/CLI → 队列 → 代持 runner → Win32 点击/输入/回车 → 回执
```

## 4. 数据流

| 方向 | 路径 | 花钱 |
|---|---|---|
| 收（回调） | 企微 → nginx:443 → 18788 → 8788 → 本地服务处理并落库 | 否 |
| 收（群/外部联系人全量） | **企微「会话内容存档」→ 存档接入（客户开通并付费）** | 存档费客户付 |
| 发 | 队列任务 → 代持 runner → 客户端界面自动化 → 回执写回队列 | 否（本地；AI 另计） |

**为什么发送必须走队列**：多客服并发点击会互相抢焦点；GUI 自动化天然慢且会失败；没有回执就回答不了「到底发出去没有」。（队列与三档发送端的设计见 `企微客服-工作台.md` §4。）

## 5. 接口

| 入口 | 形态 | 说明 |
|---|---|---|
| `POST /wecom` | HTTP（企微回调） | 需签名参数；缺参数 → **400**（这是"链路通了"的判据，不是故障） |
| `GET /health` | HTTP | 200 = 本地服务活着（不等于隧道通） |
| 隧道口 `127.0.0.1:18788`（服务器侧） | TCP | nginx 反代目标；被残留 ssh 占住会出现 `remote port forwarding failed` |
| 代持发送 CLI | CLI（D82） | 零 token，动态找窗口；供队列/人工调用 |

**排障判据**：`/wecom` 返回 **400** = 整条链通；返回 **502** = nginx 通但后端（隧道或本地服务）不通。

## 9. 排障

### 9.1 隧道 502 的三种原因（按概率排）

| # | 原因 | 怎么确认 | 处置 |
|---|---|---|---|
| 1 | **SSH 反向隧道断了**（家宽重拨/网络抖动/ssh 进程退出） | `logs\wecom-tunnel.log` 有"判死"；服务器上 `ss -ltn \| grep 18788` 无监听 | 等 keeper 自愈（最快 9s）；或按日志手工重起 |
| 2 | **本地 8788 没起来**（WeCom bridge / watchdog 挂） | 本机 `curl 127.0.0.1:8788/health` 不通 | **不重启隧道**，去修本地服务（watchdog 的活）；keeper 会记录但不乱杀 |
| 3 | **服务器端 18788 被残留监听占着**（旧 ssh 未释放） | 重起时报 `remote port forwarding failed` | keeper 每次重起前先杀匹配 `18788:127.0.0.1:8788` 的残留 ssh，再起新隧道 |

### 9.2 keeper 探针的已知缺陷：**用公网探针会自激**

- 探针打的是**公网地址**，也就是**被测对象本身**；隧道刚重建的窗口里探针仍会拿到 502 → 把"刚起来还没就绪"的隧道当死的再杀一次 → **自己杀自己刚建的隧道**（自激）；
- 现有缓解（均来自 D81 实测）：①起隧道后**等 3s 再探**；②一轮最多重试 3 次；③10 分钟内重启计数与间隔阶梯（30/60/120/300s）；④连败 5 次邮件报本体但**永不 give-up**；⑤本地 8788 守卫（见 9.1 第 2 条）。
- **还没根治**：想根治得改成「探本地服务 + 探服务器侧 18788」两段式判死，而不是只探公网——这是 03 的活，记为演进债。

### 9.3 常见命令

```powershell
curl.exe -s -o NUL -w "%{http_code}" https://theglobalscm.top/wecom   # 400=通，502=后端不通
curl.exe -s http://127.0.0.1:8788/health                              # 本地服务活着吗
Get-Content logs\wecom-tunnel.log -Tail 20                            # keeper 在做什么
ssh root@115.191.6.89 "ss -ltn | grep 18788"                          # 服务器侧隧道口
```
