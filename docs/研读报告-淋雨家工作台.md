# 研读报告 · 淋雨家的工作台（luanyujia-workbench）

> 2026-10-29 读于 `github.com/mashanglinyu/luanyujia-workbench`（main，commit 期 10-29）
> 规模：**327 个文件 / 21.5 MB**，13 个板块，JS 为主，**318 stars**
> 一句话描述（其自述）：多场景 AI 工作台：**六层总纲 + 拓扑连线图 + 公开版工作台模板（四场景可跑）+ 记忆机制**

## 一、它是什么

**同一台机器上常驻多个 AI「同事」，共用一套规则与台账，各自有独立记忆；活按项目派给 owner，干完必须留证据和回执。**

它自认最难的不是界面，而是三套机制：

| 机制 | 一句话 | 不搞会怎样 |
|---|---|---|
| **协作** | 谁说了算、谁改哪里、怎么交活、怎么算交付 | 互相踩、互相客套烧 token、活没人干 |
| **记忆** | 记忆在文件里，不在会话里 | 一换会话就"失忆"，记忆越写越肥没人读 |
| **场景体系** | 一个场景 = 一类会反复回来的活（六件套） | 全塞一个窗口：上下文互挤、权限混乱 |
| **派单（专题）** | 一条活的完整状态机 + 台账 + 销账 | 派单进黑洞、双方互等 |
| **GPU 优先（专题）** | 只有三类活能上 GPU | 白折腾（更慢），或把机器打爆 |

## 二、结构

**六层归属（每样东西只属于一层，只在一个地方是真源）**

| 层 | 放什么 | 谁能写 |
|---|---|---|
| L0 宪法 | 铁律与附则（版本化，改一次 +1，旧版留档） | 只有宿主 |
| L1 共享层 | 宿主画像 / 场景区域表 / 项目清单 / 通知待办 / 总索引 / 体检快照 | 分区写 |
| L2 场景私有 | §〇 交接（≤4KB）/ 身份卡 / 场景画像 / 项目记忆（≤8KB）/ 专属技能 / 归档 | 只有本场景 |
| L3 个人层 | 个人档案与知识库 | 本人，不进共享层 |
| L4 运行时 | 引擎 / 外壳 / 工具 / MCP / 插件 / 计划任务 | 专人维护 |
| L5 归档 | 备份 / 会话冷备 / 场景归档 | 只进不改 |

## 三、值得借鉴的做法（按对我们的价值排序）

### 1. 派单状态机里有「未回执」这个显式状态 —— 我们缺
它把一条活拆成：想出派单 → 投递（必须真唤醒） → 已投递 →（回执）→ 已回执 → 收尾知悉 → 销账，**超时无回执 → 进「我发出没回」清单**。
它的原话：**"多 AI 系统里最贵的浪费是双方都在等对方，而且它没有任何报错。"**
→ 我们今天的实例：我给 01 的决定邮件（seq=363）它没读，水位停在 361，**问了两轮才发现**。这就是"没有未回执态"。

### 2. 派单 vs 公告的唯一判据 + 一个血数字
判据只看句子：要对方**动手** = 派单（必须唤醒）；只是知道 = 公告（只落盘，不唤醒）。
它记录的实况：**一天发 36 条"通知"，只有 8 条真进对方会话**（8/36 = 22%），其余躺在记忆文件里等人点开。
→ 我们的同构事故：邮件 nudge 只敲一次，**179 条积压静默**；nudge 过期 + 每日清点就是补这个。

### 3. "发送方必须核对 DELIVERED"（血案）
它的实测：回执时用 `Select-Object -First 8` 截断输出，只看到"--wake"就当成成功，**实际 exit 1 没发出去**。
→ 我们的对应：dispatch 成功 ≠ 对方看到；**要看 `accepted` + 对方下一轮的动作**，不能看"命令没报错"。

### 4. 注入层只放铁律，细则按节号查、不注入
"每轮注入人人都在付这个成本 ⇒ 必须极短，只放'不读就会白干'的铁律，⛔ 不放教程和细则。"
→ 我们规则正文已 27 节 / 27KB+，速查 1 页的方向是对的，但**还没做到"注入内容与可查内容分离"**。

### 5. 「隐患与限制清单」的写法：每条都带实测数字 + 怎么验
它的格式：现象 / **证据（实测数字，如 4.7GB、49,871 文件、74.3MB 单文件）** / 后果 / 缓解 / **怎么验（体检项）** / 状态；分 **S（丢东西、不可逆）/ A（卡成长）/ B** 三级；并写死"⛔ 别当已修"。
→ 我们的 `坑.md` 是 10 条平铺，没有分级、没有数字、没有"怎么验"。**这是最容易补、收益最大的一条。**

### 6. 反例验收：校验工具必须能证明"该失败时会失败"
它的原则：校验类工具必须能证明"该失败时会失败"，结论要能说出**差异集合**。
→ 与我们今天的 D68 一致（改坏组必须 FAIL）；差别是它把它写成了通用规矩，我们只写进了单条验收。

### 7. 三条通用判据（他们踩出来的，比我们的"字段存在≠功能做到"更狠）
1. **"程序说成功" ≠ 成功** —— 要看外部事实变了没有（hash、200、页面上有没有新东西）；
2. **"看起来像" ≠ "指向对"** —— 路径类配置必须 `Test-Path`，端口必须真连一次；
3. **"做了改动" ≠ "生效了"** —— 先问"这改动是热更还是要重启"，再看"我验的是不是那条链路"。

### 8. 会话绑定：必须用会话 id，且"到位了没有只能看画面"
三条硬结论：①**必须给会话 id**，不能只靠标题认人（标题会重名/差空格/被改名）；②判断"到位了没有"**只能看画面**，不能看自己写的存储值；③一个 AI 面板一个独立分区，否则多面板抢同一个"当前会话"键。
→ 我们换代只核 `workspaceId` + 标题字符串；**缺"看画面"这一步**（今天新 03 读漏 D81 就是"没看画面、只凭交接包复述"）。

### 9. 负载闸：派活前先跑一遍，任一 90% 就不派
它把"上下文/负载"做成**派单前置闸门**（`负载闸.mjs`），90% 就不派子代理、不唤醒。
→ 我们是"压线才换代"（工作组 70 万/本体 95 万），**缺派单前的负载检查**——今天 06 在 681k 还在接单，是我人工发现才换的。

### 10. 临时文件只许三处 + 哨兵
只允许 `<工作区>\_临时\` 或按会话分目录，⛔ `%TEMP%`/C 盘不接受；配 `临时路径.mjs`（生成）+ `临时哨兵.mjs`（落盘前校验）。
→ 我们 `tmp\` 无人守，今天我自己就在里面留了一堆临时脚本（多数删了，但没有机制保证）。

### 11. 机制清单的思路：一条规矩 = 一个可执行动作
例："临时文件只能放三处"→ 有脚本；"插件挂了但没生效能被查出来"→ 有检查；"会话超线会主动喊"→ 有告警。
→ 我们的规则多数还停在**文字**，可执行的只有一部分（dispatch 闸、check-context-budget、mail）。

### 12. 场景六件套
一个场景 = 配置 json + 定位卡 + 身份卡 + 场景画像 + 私有记忆（§〇 交接）+ 专属技能；缺一件就不算"场景"，只是一次性对话。
→ 我们的"功能域"只有 id/name/owner，**没有领地边界与私有记忆**。

## 四、它的短板（不要照抄的地方）

1. **体量劝退**：700+ 个尖括号占位符、05 板块 190KB，作者自己都要写"小白最短路径"；
2. **强绑单机**：大量 PowerShell / Electron / 本机路径假设，**换机器要重铺**；
3. **源码照搬 21MB**：含 13MB 启动视频与 1.1MB 单文件 renderer，**不适合进 git 工作流**；
4. **数字会漂**："十余个场景/二三十个项目"这类数字它自己标注"不构成承诺"——**别把别人的规模当目标**；
5. **缺少"验收人"角色**：它有派单/回执，但没有我们"01 唯一验收人 + 硬性证据"这一层；**我们这块比它强，别退回去**。

## 五、和我们体系的对照（一句话结论）

**同构度很高**：都建立在 DSH 之上，都靠"文件而非会话"记记忆，都做派单/回执/换代。
**差别**：它是"**大规模 + 强机制**"（十几个场景、三层记忆、负载闸、体检项、隐患分级），我们是"**小规模 + 强验收**"（01 唯一验收人、硬证据、花费口径、工单编码）。

**最该学的三件**：①「未回执」显式态 + 投递确认；②隐患清单的"分级 + 实测数字 + 怎么验"；③负载闸（派单前先看目标还能不能吃）。

**最不该学的三件**：①照搬它的体量（21MB 源码 / 700+ 占位符）；②把规则写成 190KB 的长篇；③丢掉我们自己的验收权威。
