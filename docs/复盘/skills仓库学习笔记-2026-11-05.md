## 二、七个可以直接搬过来的做法

| # | 它的做法 | 我们的现状 | 能怎么改 |
|---|---|---|---|
| 1 | **两轴 review**：Standards（符合本仓规范）+ Spec（符合原始需求），**两个子代理并行** | 我们的验收只有"证据"一轴（`check-delivery`） | 给验收加"标准轴"：对照 `docs\规则-*.md` 检查，而不是只看有没有贴 exit 码 |
| 2 | **诊断先造反馈回路**：能一键 pass/fail 复现，才算开始诊断 | QQ 桥坏了我们是"看日志猜" | 给桥做 `smoke.mjs`：造一条消息 → 断言回复 → 作为回归基线 |
| 3 | **seam（缝）与深模块**：先定"在哪个公共边界测试"，再写测试 | 84 个脚本，边界混乱，`bridge.js` 1.2 万行 | 用 `codebase-design` 给桥定 3 个 seam，再谈拆分 |
| 4 | **GLOSSARY.md + docs/adr/**：术语与决策都落文件 | 没有术语表 → 才会出现"基本金额 306,436 = 保额？"这种误解 | 鹏雁项目**第一件事就建 GLOSSARY**（保单术语 + 我们自己的黑话） |
| 5 | **tracer bullet 票**：每张票都能独立跑通一条端到端路径 | 我们的票常是"大块"（IN-001 就包含三件事） | 拆成：①建空壳数据 ②跑通 1 份真件 ③检索命中 |
| 6 | **handoff skill**：交接稿有固定骨架，且明确"下一棒要干什么" | 我们有六字段交接稿，但常写不到"下一步" | 对齐它的字段（含"下一棒的入口命令"） |
| 7 | **writing-for-agents**：文档分"上下文负载"和"认知负载"，用**指针 + 分支**控制 | 我写的规则文档又长又平，读起来费劲 | 规则改成"一段话 + 什么时候读哪份"的指针结构 |

## 三、最值钱的三条（如果只记三条）

1. **「先造反馈回路」**——它说"建好回路，bug 已经修好 90%"。我们这几天在桥上反复踩，就是因为**没有一键复现**。
2. **「两轴 review」**——只验"有没有证据"是不够的，还要验"符不符合原来的需求"。我们错的正是这一轴（WC-004 发错人、UG-043 判据没跑）。
3. **「文档是给 agent 的地图，不是给人看的散文」**——所以要有 GLOSSARY、ADR、指针，而不是把所有东西塞进一个 md。

## 四、和现有体系的冲突点（要认）

| 冲突 | 说明 |
|---|---|
| 它假设有 **git + issue tracker**（GitHub/Linear） | 我们是"台账 + 项目栏 + 交付文件"，没有 issue tracker；要移植得先做映射 |
| 它的票是**给 AI 自己看的**（to-tickets 直接写进 tracker） | 我们的票是给工号看的，格式更重 |
| 它偏**单人 + 单仓** | 我们是多工号、多项目、有额度与负载闸 |
| 部分 skill 依赖 `/setup-matt-pocock-skills` 初始化 | 那套初始化是给 Claude Code 的，DSH 里跑不了，需要改造 |

**结论：不能照搬，但骨架能拆下来用。**
