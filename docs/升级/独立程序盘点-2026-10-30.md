## 一、判定标准（沿用草案，补一句）

够格做成独立 exe：①不依赖 DSH 的对话能力（无 LLM 也能跑）②有稳定 I/O（端口/文件/HTTP）③需长期活着或定时跑 ④坏了要能自己重启（有守护价值）。
**补充**：⑤**故障隔离价值**——合并后一处崩溃会带死另一处时，宁可不合并（这决定了下表的合并边界）。

## 四、双模式评估（`--shell` + `--service` 同一个 exe）

**结论：不做"同一二进制双模式"，改做"一个启动器 + 两个组件"。**

| 方案 | 做法 | 风险 | 判断 |
|---|---|---|---|
| A 同一 exe 双模式 | C# 壳里嵌 Node 运行时，`--service` 时只跑服务 | **高**：把 node 塞进 .NET 宿主要么引 hostfxr/SEA 嵌壳，要么用 C# 重写工作台；两侧调试链全变，出问题定位成本翻倍 | ❌ 不建议 |
| **B 启动器 + 两组件**（推荐） | `Xunyu.exe`：双击=先起 `XunyuWorkdesk.exe --service`（后台）再起 `XunyuWebWindow.exe`（窗口）；`Xunyu.exe --service`=只起服务 | 低：两个 exe 各自仍是现在这套技术栈，启动器只管进程编排（起/停/托盘/退出时收尾） | ✅ 建议 |
| C 完全分开（现状） | 用户自己开两个 | 无风险但**体验差**（主人要的是"一个程序"） | 过渡期保留 |

**B 的必做细节**：①启动器要能在窗口关闭时**不杀服务**（服务继续跑），托盘菜单提供"退出全部"；②服务已在跑时再双击窗口 = 只开窗口（单实例锁）；③服务崩溃时启动器/守护负责拉起（交给 `XunyuGuard.exe`）。

## 六、明确不做（6 条，各一句理由）

1. **不把 DSH 本体打包**——它就是宿主，打包等于把宿主塞进自己肚子里。
2. **不给 5 个 MCP 进程做 exe**——它们是 DSH 插件（`qq-bridge\plugins\`），生命周期跟宿主；打包会与 DSH 争同一份配置。
3. **不引 `pkg` / NSSM / Electron**——pkg 已停更、NSSM 是外部依赖（红线上写"别引"）、Electron 等于把已跑通的 WebView2 壳推翻重做。
4. **不合并 QQ 桥与工作台/内环**——bridge 是 835KB 上游魔改 + 外网连接，必须独立故障域。
5. **明天不做 VM 内 `XunyuVmAgent.exe`**——依赖 WC-004（watcher）尚未实现，做出来没处验。
6. **一次性 CLI 不打包**（`add/dispatch/accept/drop`）——保持 `.mjs` 可直接改、可调试；打包后改一行要重打 80MB。

## 七、遗留与风险

1. **`findings-sync.mjs` 未落地**：草案把"findings"列进 Ops，实际文件不存在（`current-task.md` 记的 WC-013 是这个计划）。打包前需 04 先落地，否则 Ops 里少一块。
2. **9341（客服工作台后端）未起**：它是给甲方部署的产品，不属本机常驻清单；打包时要单独出 `XunyuCsServer.exe`，别混进本机 exe。
3. **SEA 体积与签名**：70–90MB × 5 个 exe ≈ 400MB，且首次运行会被 SmartScreen 拦（需主人放行/签名）——这个成本要主人认。
4. **内存流水线目前靠计划任务**，做成 `XunyuMemory.exe` 收益有限（一天跑几次），列入"后天"而不是明天。
5. **合并的代价**：`XunyuBridge` 把四个进程合一个后，一处 OOM 会全挂（现在只挂一条腿）——所以第 4 项的判据里强制要求"守护 30s 内拉起"。
