> **一句话**：五个 exe、常驻从 **12 → 3**（+1 按需 +1 在 VM），全部 **Node SEA** 单文件，**计划任务**自启，`XunyuGuard` 统一拉起。

## 2. 入口约定

**每个 exe 的入口都是 `<repo>\src\<exe>\main.mjs`**，构建时打成 CJS bundle 再塞进 SEA。

| exe | 默认模式（不带参数） | `--service` | `--once <子命令>` | `--dry-run` |
|---|---|---|---|---|
| XunyuGuard | `--service` | 常驻守护 | `--once status` 打印受管进程/端口表 | 只打印将执行的动作，不杀不起 |
| XunyuBridge | `--service` | 常驻四服务 | `--once probe` 探四个端口各一次 | 只做端口探测不写日志 |
| XunyuWorkdesk | `--service` | 常驻 HTTP | `--once health` 打印 `/api/health` 结果 | 起服务但**不写盘**（不落 state/日志） |
| XunyuOps | `--once help` | `--service`＝按 `config\app.json` 的 schedule 表跑定时 | `--once <命令> [参数]`（如 `--once mail tail --as 01`） | 所有写操作只打印不执行 |
| XunyuVmAgent | 必须给 `--role host\|vm` | 常驻对应角色 | `--once send --conv X --text Y` | 只模拟，不发 |

**通用参数（五个 exe 都认）**：`--root <dir>` · `--config <dir>` · `--log-dir <dir>` · `--version` · `--help`。
**退出码（统一）**：`0` 成功 · `1` 运行失败 · `2` 用法错 · `3` 依赖不可用（端口/文件/DSH API）· `4` 被拒绝（配额/守卫）。
**环境变量**：`XUNYU_ROOT` / `XUNYU_CONFIG` / `XUNYU_LOG_DIR` / `XUNYU_MODE`。
**启动即写一行**：`logs\<exe>.log` 第一条 = `version, mode, root, pid`（排障第一现场）。

## 3. 构建（Node SEA，Node 22+；本机 Node 24 已验证可用）

```powershell
# 一次性（构建机）
npm i -D esbuild postject

# 单打一个 / 全打
node scripts\build-exe.mjs --exe workdesk
node scripts\build-exe.mjs --all
```

**`sea-config.json` 示例（由 build-exe.mjs 按 exe 生成，不需手写）**

```json
{
  "main": "dist/bundle/workdesk.cjs",
  "output": "dist/blob/workdesk.blob",
  "disableExperimentalSEAWarning": true,
  "useCodeCache": true,
  "assets": { "version.txt": "dist/bundle/workdesk.version.txt" }
}
```

**手工等价命令（照抄可跑，以 workdesk 为例）**

```powershell
npx esbuild src\workdesk\main.mjs --bundle --platform=node --format=cjs --outfile=dist\bundle\workdesk.cjs
node --experimental-sea-config sea-config.json
Copy-Item (Get-Command node).Source dist\XunyuWorkdesk.exe -Force
npx postject dist\XunyuWorkdesk.exe NODE_SEA_BLOB dist\blob\workdesk.blob --sentinel-fuse NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2
```

**`scripts\build-exe.mjs` 职责（04 写，UG-029）**

| 职责 | 细节 |
|---|---|
| 读清单 | `build\exes.json`：exe 名 → 入口 → 需要哪些 asset → 目标文件名 |
| 打包 | 先 `esbuild --bundle --format=cjs` 到 `dist\bundle\<exe>.cjs`（**Node 内置模块 external，第三方依赖必须 bundle 进来**） |
| 生成 blob | 写临时 `sea-config.json` → `node --experimental-sea-config` → `dist\blob\<exe>.blob` |
| 注入 | 复制当前 node.exe 到 `dist\<Exe>.exe` → `postject` 注入（sentinel 固定值） |
| 校验 | 跑 `dist\<Exe>.exe --version`，退出码非 0 即失败；打印体积与 SHA256 |
| 汇总 | 写 `dist\manifest.json`（含 node 版本、各 exe 体积/hash、构建时间） |
| 参数 | `--exe <name>` 单打、`--all` 全打、`--no-inject` 只出 bundle（调试用） |
| 失败处理 | 任何一步失败立即非 0 退出，**不删已有产物**（便于对比） |

## 4. 目录与配置（**exe 内不写死路径**）

```
<root>\                     # 解析顺序见下，默认安装根的父级
├─ config\
│   ├─ app.json             # 端口表、schedule、开关（人可读）
│   ├─ exe.json             # 每个 exe 的 mode/role/ports
│   └─ secrets.json         # 凭据（不入 git、不打进 exe）
├─ logs\                    # <exe>.log 按天滚动，保留 30 天
├─ state\                   # 台账/项目/邮件/缓存（与原 state 同构，可整体搬走）
└─ dist\                    # 构建产物（只在构建机）
```

**root 解析顺序（写进 `src\common\paths.mjs`，五个 exe 共用）**：`--root` → `XUNYU_ROOT` → exe 所在目录若含 `config\` 则用它 → `%ProgramData%\Xunyu`。
**红线**：源码里出现 `E:\` 字面量即构建失败（`build-exe.mjs` 加一条 grep 检查，纳入 §3 校验步）。

## 5. 服务与自启（**确定答案：计划任务**）

| 场景 | 答案 | 命令 |
|---|---|---|
| Guard / Bridge / Workdesk 开机自启 | **计划任务（登录触发 + 最高权限）** | `schtasks /Create /TN "Xunyu\Guard" /TR "\"<root>\dist\XunyuGuard.exe\" --service" /SC ONLOGON /RL HIGHEST /DELAY 0000:10 /F` |
| VM 内 VmAgent | **计划任务（VM 开机/登录触发）** | 同格式，`--role vm` |
| Ops 定时 | **不注册**，由 Guard 内部 schedule 表触发 `XunyuOps --once <cmd>` | — |

**为什么不是 `sc create`**：①窗口壳、截图、Win32 输入在 **Session 0 服务里不可用**；②现在的守护（supervisor）本来就是计划任务，迁移零成本；③服务需要自己实现 SCM 握手（DispatchTable），今晚做不完。
**失败回退**：若确实需要"无人登录也跑"，只对 **Bridge / Workdesk / Guard** 三个无 GUI 的启用服务模式：`sc create XunyuGuard binPath= "\"<root>\dist\XunyuGuard.exe\" --service" start= auto`（需 04 加 `--service` 的 SCM 握手分支）；**VmAgent 与任何带界面的永不进服务**。回退到计划任务：`sc delete XunyuGuard` + 重建任务，1 分钟。
**双守护禁令**：切换期**同一职责不许两套守护同时在跑**（Guard 接管谁，旧的 supervisor 就从名单里划掉谁），否则互相重启会打死进程。

## 6. 守护关系（Guard → 另外四个）

| 受管 | 存活判据 | 重启顺序 | 退避 | 上限 |
|---|---|---|---|---|
| Bridge | 9334+9335+9339 三端口在听 **且** `/health` 200 | 第 1 | 1s→5s→15s→60s→300s | 10 分钟内 ≥5 次 → 邮件报本体 + **停止重试**（转人工），不再狂拉 |
| Workdesk | 9340 与 8788 均 `/health` 200（9342 可选） | 第 2 | 同上 | 同上 |
| VmAgent(host) | 18766 在听 | 第 3 | 同上 | 同上 |
| Ops | 不监控（跑完即退）；失败靠退出码 + 邮件 | — | — | — |

- **拉起顺序**：Guard 自身 → Bridge → Workdesk → VmAgent（Workdesk 依赖 9334）。
- **探测频率**：5s 一次 TCP，30s 一次 `/health`（避免打爆日志）。
- **Guard 自己**：计划任务 `Xunyu\Guard` + 一个 `Xunyu\GuardWatchdog`（每 5 分钟，检查 Guard 进程在不在，不在就起）——**两级，别加第三级**。
- **日志**：Guard 记 `logs\guard.log`：`探测→判死→杀残留→起进程→恢复`，每行带 pid 与耗时。

## 8. 整单回滚（exe 方案整体失败时怎么回脚本态）

**一句话**：脚本态是本方案的**母体**，不是被替换掉的旧东西——`scripts\` 与 `.ps1` **全量切换后仍保留 2 周**（建议：5 个 exe 全部接管且稳定运行 7 天 → 再保 14 天 → 约 **2026-11-13** 到期）。到期不删，按 §十三 只标记进 `backup\scripts-retired-<日期>\`。

| 对象 | 回滚后怎么处理 | 会不会丢东西 |
|---|---|---|
| `scripts\*.mjs` / `*.ps1` | **保留到 2026-11-13**；期间 exe 出问题直接用它起 | 不丢（文件一直在） |
| `dist\*.exe` | **弃用 ≠ 删除**：改名 `dist.failed-<日期>\` 留着取证 | 不丢 |
| `config\` `logs\` | 保留（脚本态也读同一套 config，路径兼容） | 不丢 |
| **`state\`** | **完全不受影响**：台账/项目/邮件/缓存都是纯数据文件，exe 与脚本读写同一目录 | 不丢（这是刻意设计：二进制可回滚，数据不回滚） |
| 计划任务 | Guard 任务禁用；旧的 `XunyuAvatarSupervisor` 保持 Running（今晚它本来就还在守 bridge/relay） | — |

**回滚命令（5 条，按顺序跑）**

```powershell
# 1) 停掉新守护，别让它把旧进程再拉起来
schtasks /Change /TN "Xunyu\Guard" /DISABLE ; schtasks /End /TN "Xunyu\Guard"

# 2) 确认旧守护在跑（它今晚没被替换，通常已是 Running）
Get-ScheduledTask -TaskName XunyuAvatarSupervisor | Select TaskName,State
schtasks /Run /TN "XunyuAvatarSupervisor"

# 3) 用脚本态把工作台起回来（若它是新 exe 起的、现在没人管）
Start-Process node -ArgumentList 'scripts\workdesk-server.mjs' -WindowStyle Hidden

# 4) 新产物移走（不删，留证）
Move-Item dist "dist.failed-$(Get-Date -f yyyyMMdd-HHmm)" -Force

# 5) 核对六个端口都在听（9334/9335/9339/9340/9342/8788）
Get-NetTCPConnection -LocalPort 9334,9335,9339,9340,9342,8788 -State Listen | Select LocalPort,OwningProcess
```

> **一条硬规矩**：回滚**不碰 `state\`**、不动 `records\`、不删任何脚本。谁在回滚时删了数据，按 §十三「删文件 = 事故」处理。
