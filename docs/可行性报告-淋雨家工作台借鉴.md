# 可行性报告 · 淋雨家工作台借鉴（哪些能抄 / 哪些要魔改 / 哪些只参考）

> 2026-10-29 · 05 主笔（依据：`tmp\luanyujia\` 16 份原文 + 本体《研读报告-淋雨家工作台.md》《升级指南-鲟鱼项目.md》）
> **引用口径**：只写对方的**做法与结论**，不贴大段原文；不落对方路径与会话 id，也不写我方凭据。
> 分拣结果：**A 可照搬 6 · B 要魔改 8 · C 只参考 5 · D 不碰 4**

## 一句话结论

**最大的三个价值**：
1. **把"没回执"变成状态**——多 AI 系统里最贵的浪费不是干错，是双方都在等却没有报错；它把这件事做成台账里的显式态，我们目前只靠人记（今天就有漏读两轮才发现的事）。
2. **给隐患分级并带实测数字**——它的 S/A/B 三级 + "证据（实测数字）· 后果 · 缓解 · 怎么验"四段，是我们 `docs\坑.md` 十条平铺最容易补、收益最大的一步。
3. **派单前先看对方吃不吃得下**——负载闸（90% 不派）把"压线才换代"的人肉判断变成了闸门，直接治我们"681k 还在接单"的病。

**最大的三个坑**：
1. **体量诱惑**：21MB 源码 / 700+ 占位符 / 190KB 规矩——照抄会把我们"少而硬"变成"多而全两头不靠"。
2. **机制错位**：它是单机强绑（PowerShell + Electron + 本机路径），换机器要重铺；我们一旦绑上，18 个工号的可移植性就没了。
3. **丢掉验收权威**：它**没有**"唯一验收人 + 硬证据"这一层；这是我们的强项，学它之前先别把它拆了。

## A. 可直接照搬（零代码耦合 / 只改文档）

**A1 · 隐患清单分级模板**
- **他的依据**：`08-升级与改造清单_隐患与限制清单.md`——分 **S（丢东西、不可逆）/ A（卡成长）/ B** 三级，每条四段「现象 · **证据（实测数字）** · 后果 · 缓解 · **怎么验**」，并写死"⛔ 别当已修"，S 级每月复核。
- **我们的落点**：`docs\坑.md` 十条平铺 → 改成分级四段式。
- **改动量**：S（把现有 10 条补数字与"怎么验"即可，不新增条目）。
- **风险**：低。唯一风险是"数字来源不可考"——允许写"未实测（待补）"，但不许编。

**A2 · 三条通用判据**
- **他的依据**：`05-协作与规矩_一-全局铁律.md` 踩出来的三条：①**程序说成功 ≠ 成功**（要看外部事实变了没：hash/200/页面有没有新东西）②**看起来像 ≠ 指向对**（路径必 `Test-Path`、端口必真连一次）③**做了改动 ≠ 生效**（先问"热更还是要重启"，再看"验的是不是那条链路"）。
- **我们的落点**：`规则速查.md` 加一条"三条判据"；规则 §八 判定 6 引用它。
- **改动量**：S。
- **风险**：低。我们已有类似表述（"字段存在≠功能做到"），这三条更狠、更可操作，属替换升级。

**A3 · 派单 vs 公告的唯一判据**
- **他的依据**：`00-核心机制_四-派单机制.md` §2 一张表——**要对方动手 = 派单（必须唤醒，花对方一轮）**；**只是知道 = 公告（只落盘，不唤醒）**。
- **我们的落点**：规则 §四（通信分级）+ §六（建单与派单）各加一句判据，避免"该派单的发了公告"。
- **改动量**：S（一句话）。
- **风险**：低。但要注意：我们的"活"邮件本质就是公告带唤醒，判据写死后要定义"活"的边界（建议：只有"必须 24h 内动手"才配 `level=活`）。

**A4 · 每轮注入只放铁律**
- **他的依据**：注入层（`全局铁律`）**每轮自动注入，所以必须极短**——只放"不读就会白干"的铁律，教程与细则一律放另一份按节号查；并给了引擎 64KB 上限的提醒。
- **我们的落点**：`规则速查.md`（一页 20 条）就是我们的注入层；细则继续留在 `规则-开发与维护.md`，速查里每条只给"节号指针"。
- **改动量**：S（D71 已把 35 节压到 15 节，这步是"把速查正式定义为注入层"）。
- **风险**：低。风险在"指针失效"——规则改节号时速查的指针要同步，纳入每日复盘检查项。

**A5 · 反例验收**
- **他的依据**：`05-全局铁律` 写死「**"必然合格"的自证 = 假证**」：自证/核对/体检类工具必须把被核对象**排除在比对集合外**、带一个**应当失败的反例**、结论要能说出**差异集合**（不是只给一个 0）。
- **我们的落点**：规则 §八 判定 6 后面补一句"校验类交付必须带一个应当失败的反例"；`模块契约` 与 `module-doctor` 的验收同此。
- **改动量**：S。
- **风险**：低。注意别变成"每次都要造反例"的形式主义——只对**校验/体检类**交付强制。

**A6 · README 板块化索引 + 最短路径**
- **他的依据**：`README.md` 用一张板块表 + "你现在在哪一格"的最短路径（新手/踩坑/升级各一条），而不是把所有内容铺在前面。
- **我们的落点**：`docs\projects\_INDEX.md`（已有一版）+ `工作组必读.md`（谁读什么）；补一条"按处境找入口"的短表。
- **改动量**：S。
- **风险**：低。风险是索引本身腐化——纳入每日复盘（D71 已有：速查/分册当天更新）。

## B. 需要魔改（写清"改对方哪一处 / 改我方哪一处"）

> "对方"= 那套实现思路里具体的一处机制；"我方"= 我们的脚本/数据/页面。B 类没有一条能"整段搬"，因为两边跑的东西不同（他们是单机 Electron 壳，我们是 DSH 多会话 + WebView2 壳）。

**B1 · 派单状态机加「未回执」态**
- **他的做法**：一条活的状态机末段是「投递（必须真唤醒）→ 已投递 →（回执）→ 已回执 → 收尾知悉 → 销账」，**超时无回执 → 进"我发出没回"清单**；投递记录里有 `delivered` 与 `ack` 两个字段。
- **我们现状**：`worklist-core` 有 `inbox→proposed→queued→doing→submitted→done/dropped`，**没有"发出去了但对方没动"这个概念**；只能靠人记（今天就有漏读两轮才发现）。
- **改对方侧**：不改代码——只移植"未回执"这个**语义**与清单概念（对方的失败判据"双方互等且无报错"直接引用进我们的验收口径）。
- **改我方侧**：①`worklist-core.mjs` 加派生字段 `deliveredAt` / `ackAt` 与派生态 `unacknowledged`（**不改原状态机**，只做派生态，同 D30 的 `blocked` 做法）；②`dispatch-core.mjs` 在成功投递时写 `delivered:{at}`，收到 `submitted` 时写 `ack`；③超时（默认 30 分钟）由 workdesk 的定时器算出来，不写死状态；④页面顶部加"我发出没回：N"。
- **工作量**：M。
- **风险**：中。派生态与真实状态容易打架（同 D63 踩过的坑）——必须写死"派生态只影响显示与提醒，不改状态机"。
- **怎么验**：造一张票派给不相干的会话 → 30 分钟后派生态变 `unacknowledged`、清单 +1、顶部数字变；对方一交活 → 派生态消失。反例：派人真收到时不出现。

**B2 · 投递确认（核对"对方真的收到了"）**
- **他的做法**：发送方必须核对 **DELIVERED**，不能拿"命令没报错"当成功——他们有一次用输出截断把 `--wake` 当成发成功，实际 exit 1 没发出去。
- **我们现状**：`mail.mjs` 只返回 seq，不报对方读水位；`dispatch` 只拿 `accepted`。`mail` 的水位文件 `<agent>.read` 其实已是现成的"对方读到哪"。
- **改对方侧**：把"必须核对投递结果"作为投递类动作的**验收判据**（引用其血案结论）。
- **改我方侧**：①`mail.mjs` 新增 `verify --as <agent>`（读水位 + 报未读条数）与 `post --require-read`（发完 10 分钟回查水位，未动则重投一次）；②`dispatch-core` 在审计里记 `accepted` 与"目标水位"；③验收口径：投递类交付必须贴**对方侧证据**（水位变化/对方下一轮动作）。
- **工作量**：S。
- **风险**：中。重投可能与 nudge 打架（同一封信被敲两次）——用 `idemKey` 去重，且"重投"只对 `level=活`。
- **怎么验**：发给一个停工会话 → 10 分钟自动重投一次（贴两次 seq）、20 分钟报本体；对方读了 → 不再重投。

**B3 · 派单前置负载闸（90% 不派）**
- **他的做法**：派单前跑"负载闸"，任一目标到 **90%** 就不派、不唤醒；把"上下文/负载"做成派单的**前置门**而不是事后补救。
- **我们现状**：只有"压线才换代"（工作组 70 万 / 本体 95 万）+ `409 worker-has-doing`；**没有"快满了就别派"**（今天 681k 还在接单，人眼发现）。
- **改对方侧**：阈值语义（"90% 只管 P0 直派、需 `--force` 记审计"）——我们按自己的换代线换算，不照抄它的数字。
- **改我方侧**：①`dispatch-core.mjs` 在派发前读目标 `pressureTokens`（复用 `check-context-budget.mjs` 的读取逻辑）；②≥ 线−5 万 → 拒派并提示"先换代"；≥90% → 仅 `--force` 放行并写审计；③`worklist.mjs dispatch` 透出拒绝原因。
- **工作量**：S。
- **风险**：中。可能把"该派的活"挡住 → 必须留 `--force` + 审计 + 明确提示，绝不静默失败。
- **怎么验**：把某工号上下文占位改到线上 1 万内 → dispatch 被拒、提示"先换代"（贴）；`--force` 能过且审计里有一条。

**B4 · 换代"看画面"验证**
- **他的做法**：会话绑定必须给会话 id（不能只靠标题，标题会重名/差空格/被改名）；判断"到位了没有"**只能看画面**，不能看自己写的存储值。
- **我们现状**：换代核 `workspaceId` + 标题字符串 + 复述；今天有"新 03 读漏前置单，只凭交接包复述"的事故。
- **改对方侧**：不改——把"判据只能是画面"引用为验收口径。
- **改我方侧**：①`handoff.mjs` 的交接包要求附**新会话截图**（标题/工作区/头像区都在画面里）；②规则 §十一 加一句"无画面证据 = 交接未完成"；③`handoff` 校验截图文件存在且 mtime 在交接后。
- **工作量**：S。
- **风险**：低。截图靠人贴，可能贴旧图 → 校验 mtime + 画面里要有当次交接稿文件名。
- **怎么验**：下一次换代交付里带图；无图 → 01 打回（用一次真实换代验证）。

**B5 · 临时文件哨兵**
- **他的做法**：临时文件只许落指定两处（工作区 `_临时\` 或按会话分目录），`%TEMP%`/C 盘不接受；配"生成路径"与"落盘前校验"两个脚本，体检里扫残留。
- **我们现状**：`tmp\` 无守卫（我自己就扔过十几个脚本），没有清理机制。
- **改对方侧**：只借"落盘前校验 + 每日清理 + 体检扫残留"三件套的**结构**；目录名与清理策略按我们的（`tmp\<会话短id>-<时间>\`，清 7 天）。
- **改我方侧**：①新增 `scripts\tmp-guard.mjs`（校验目标路径是否合规，供各工具调用）；②`tmp\` 加 `.gitignore` 与 `_README`（写规则）；③每日 04:00 清理任务只清 `tmp\`，日志计数。
- **工作量**：S/M。
- **风险**：中。清理脚本误删风险 → 只匹配 `tmp\` 且 `-WhatIf` 先跑一次、白名单 `_README`。
- **怎么验**：往 `tmp\` 根写文件 → 被 guard 拒或自动归档；清理日志有删除计数；`-WhatIf` 试跑清单与实际一致。

**B6 · 功能域"六件套"**
- **他的做法**：一个"场景"由六件构成（配置 / 定位卡 / 身份卡 / 场景画像 / 私有记忆（§〇 交接）/ 专属技能），缺一件就不算场景、只是一次性对话。
- **我们现状**：`projects.json` 的功能域只有 `id/name/owner/parallel/contract/blockedByDomain/tickets`，**没有领地边界、没有私有记忆、没有归档**。
- **改对方侧**：只借"缺件即不合格"的判据；六件按我们的东西换算成 **4 件**（不贪多）：`README`（做什么/不做什么）· 私有记忆（当前状态与卡点）· 专属脚本或面板（可空但声明）· 归档目录（只进不改）。
- **改我方侧**：①`projects.json` 的 feature 加 `readme` / `memory` / `artifacts` / `archive` 四个字段（可为 null，但必须显式声明）；②`module-doctor.mjs` 加检查：缺件报 ⚠；③先拿 `wecom-relay` 试点。
- **工作量**：M。
- **风险**：中。字段一多就变成填表游戏 → 只强制"声明"，内容可以为空并标"未建"。
- **怎么验**：`module-doctor` 对试点域报"4/4 齐"；故意删一个字段 → 报 ⚠（反例）。

**B7 · 机制清单（一条规矩 = 一个可执行抓手）**
- **他的做法**：单开一页"机制清单"，每条写「判据 / 抓手 / 验证方式 / 失败时怎么办」，并注明哪些规矩已从"靠自觉"变成"靠机制"（工具/体检/计划任务）。
- **我们现状**：规则 15 节，真正有闸门的只有少数（dispatch 闸、`check-context-budget`、`mail`、依赖链），其余多为文字。
- **改对方侧**：借"抓手"概念与四列结构；不搬它的清单内容。
- **改我方侧**：①规则表加一列 `抓手`（空 = 纯文字规则）；②`规则速查.md` 每条尾部标 `[闸]`/`[查]`/`[文]`，`[文]` 占比目标 ≤30%；③每日复盘时把新出现的"文字规则"标出来。
- **工作量**：S。
- **风险**：低。风险是"为标而标"——允许长期 `[文]`，不强求每条都有闸门。
- **怎么验**：`规则速查.md` 15/20 条带标记、`[文]` ≤30%；抽 3 条 `[闸]` 实际跑一次闸门。

**B8 · 面板类型注册（24 类面板）**
- **他的做法**：面板类型表 + 渲染器注册机制（加一种新面板只需六步，含可拷贝代码），真实用过 24 种 / 7 族。
- **我们现状**：WebView2 壳的三栏 + 工作台页签是**写死的几块**，没有任何"注册一种新面板"的能力。
- **改对方侧**：**不能照搬**（Electron/其渲染器表与我们的 C# 壳不兼容）；只能借"类型表 + 注册函数"这个抽象。
- **改我方侧**：①壳里定义 `panel(kind, title, html)` 注册表（前端 JS 层，不动 C#）；②先实现 3 类（列表 / 详情 / 状态条）；③后续新面板只加注册项。
- **工作量**：L。
