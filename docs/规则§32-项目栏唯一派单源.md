# 规则 §32 · 项目栏是唯一的派单源（2026-10-30 03:40 主人定）

> 主人原话：
> 「后续派单流程是 05 出完项目找 01 审核，审核完就贴项目表，之前的项目里面的就加进去更新，新的就开新项目栏清单，给出优先级和派发对象，之后的任务从项目栏派发，审核后回到项目栏更新状态，01 和你追查项目进度只看项目栏里面哪些做了哪些没做」

## 一、流程（五步，责任到人）

```
① 05 出项目       → 项目分解（功能域 + 票 + 优先级 + 派发对象 + 判据）
② 01 审核         → 只审"能不能执行"：边界清楚？判据可验？依赖合理？人选对？
③ 贴项目表        → 写进 state\projects.json（已有项目=更新；新项目=新建栏）
④ 从项目栏派发    → dispatch 的候选集 = 项目栏里"依赖已清、未完成"的票
⑤ 审完回写状态    → 票的状态（queued/doing/submitted/done）投影回项目栏
```

**追进度只看项目栏**：01 与本体**不查散票**，只问"项目栏里哪些做了、哪些没做"。

## 二、项目表要求（每个功能域必须给齐）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 功能域 id（如 `auto-exe`） |
| `name` | ✅ | 人话名字 |
| **`priority`** | ✅ | **P0/P1/P2**，决定派发顺序（同优先级内按依赖） |
| `owner` | ✅ | 派发对象（工号） |
| `parallel` | ✅ | 是否允许并行 |
| `contract` | ✅ | 产出契约（接口/文件名） |
| `blockedByDomain` | ✅ | 依赖的其它功能域（解锁树） |
| `tickets` | ✅ | 票据清单（项目栏列的就是这些） |
| `note` | ✅ | 一句话状态与坑 |

**票的状态不回填 projects.json 本体**，而是**运行时投影**（`/api/projects` 里算出来），避免两个真值来源。

## 三、派发与回写（技术口径）

1. **派发源**：`dispatch` 不给单据号时，从项目栏取候选：
   `priority 升序 → 依赖已清 → owner 空闲 → 并发上限内`；
2. **回写**：票 `submitted/done` 时，项目栏对应 feature 的 `note` 自动追加"最近一次进度 + 时间"（脚本生成，不许人手改）；
3. **冲突**：票的 `project/feature` 与项目栏不一致 → `dispatch` 拒绝并提示"先贴项目表"。

## 四、验收（明天的实施单）

1. 项目栏里 P0 未完成的票 → 优先派；P0 全完成才派 P1；
2. 票 done 后，项目栏 `note` 自动出现进度行；
3. 票与项目栏 feature 不匹配 → 拒绝派发；
4. **看板/窗口"项目"页签**能一屏看出：每功能域 **P? / owner / 已完成 x/y / 当前卡点**。

## 五、立即生效的约定（不需要等实现）

- **从此刻起，新单必须先落项目栏再派**；散单（项目栏里查不到的票）**一律不派**；
- 05 出的项目分解，**没经过 01 审核不许进项目栏**。
