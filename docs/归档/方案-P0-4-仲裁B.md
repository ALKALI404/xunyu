> 目标：让「本体 / 窗口 / 工作组」三个发声源**按优先级和配额**共用同一具身体，
> 谁都不许把身体刷爆，也没人能被饿死；用户自己说的话永远不丢。
>
> 状态：**已落地并验收（2026-10-25 20:30）** —— 主套件 16/16、丢弃套件 4/4、饥饿保护日志实证、真身体回归通过。

## 2. 设计

### 2.1 角色 → 优先级

| 角色 | 优先级 | 谁 |
|---|---|---|
| `owner` | 3 | 本体：鲟鱼 tab 的回复（中继推） |
| `window` | 2 | 窗口：**用户亲自**发的句子（`manual:true`，暂未接线，预留） |
| `dev` | 1 | 工作组：DSH tab 的回复 |

### 2.2 配额（滑动窗口：角色 × 类别）

| 角色 | say | 动作（anim/emotion/dialogue/chatpanel/timer/cancelalarm） |
|---|---|---|
| `owner` | 1/3s、4/10s、15/60s | 1/2s |
| `window` | 1/2s、6/10s、20/60s（人自己说话，比本体松一档） | 1/2s |
| `dev` | 1/5s、6/60s（测试别刷屏） | 1/5s |

**超额不拒绝，而是延后**：算出该角色「最早可发时刻」= max(三条窗口各自的下个空位)，
把 job 排到那个时刻。延后期间，**同角色、尚未开始**的 `say` **合并**成一条
（用全角空格拼接，总长 ≤ 200 字，超出截断并记 `droppedChars`）。

> 3 秒内的连续 spam 才会被合并；正常对话（间隔 > 3s）完全不受影响。

### 2.3 排队与优先级

- 取下一个 job：`boosted` 先于一切 → 否则按 `(priority desc, seq asc)`。
- 单飞保持：当前 job 跑完才取下一个（身体是 Unity 主线程，不能并发）。
- **饥饿保护**：任何 job 等待 > **30s** → `boosted = true`，下一轮立刻排到最前（不受优先级压制），
  日志 `[仲裁] 饥饿保护：say@dev 等了 31.2s`。
- **队列上限 20**：超限依次丢 `dev` 最旧 → `window` 非 manual 最旧 → `owner` 最旧；
  `manual:true` **永不丢**（若 20 条全是 manual，临时超限并告警）。
  被丢的请求仍 `reject`（错误码 `QUEUE_FULL`），**绝不静默吞掉**。

### 2.4 可观测

- `/state` **追加**字段（不破坏现有 `history`）：
  ```json
  "queue":[{ "id":3,"action":"say","role":"dev","source":"relay","queuedAt":...,"priority":1,"boosted":false,"mergedCount":0,"manual":false }],
  "roles":{ "owner":{"nextAt":...,"saidLast60s":2,"actionsLast10s":0}, ... }
  ```
- 合并 / 丢弃 / 提级各写一行日志。

### 2.5 开关（回退）

- `AVATAR_BODY_ARB=off` → 完全退回今天的 FIFO 行为（便于 A/B 对比与出问题回退）。
- `AVATAR_BODY_ARB_MAX=20` 可调队列上限。

### 2.6 明确不改

适配器层、HTTP 路由、鉴权矩阵、`/health` 语义、`relay` 的调用方式（只是角色已经传进来了）。

启动方式：`$env:AVATAR_BODY_PORT=9336; $env:AVATAR_BODY='noop'; node body-service.mjs`

| # | 用例 | 断言 |
|---|---|---|
| 1 | owner 零间隔连发 3 句 | 第 1 句立即；后两句合并为 1 句（`mergedCount=2`）；发出间隔 ≥ 3s |
| 2 | owner 60s 内连发 20 句 | 实际发声 ≤ 15；无 429；截断字数与日志一致 |

| 4 | dev 1 句在队 + owner 持续刷 | dev 那句 ≤ 30s+2s 内被放行（饥饿保护） |

| 6 | 无令牌 / dev 调 timer | 仍 403（回归，鉴权不受影响） |
| 7 | 真身体回归 | 让鲟鱼说一句 → 游戏里正常显示；`/state` 里 `role=owner` |

## 5. 自查：哪些已核对、哪些是假设

**已核对（读代码确认）：**
1. 单飞/队列/丢弃策略与位置 —— 见 §1。
2. `enqueue()` 是唯一入队入口，8 个动作 case 都走它 → 加角色/优先级只需改这一个函数 + `drain()` 取队方式。
3. `/state` 的 `history` 是追加的数组，加字段不会破坏窗口/脚本。
4. 鉴权在入队**之前**执行（P0-4 第一刀），所以被拒的请求根本进不了队列 → 不影响配额计数。
5. 中继已经按目标传角色，`pushToBody` 是唯一入口 → 优先级信息现成就有。

**假设（落地时验证）：**
1. `window` 角色暂无调用方 → 优先级 2 空转；等窗口的用户发言接线后才有意义（不影响本次正确性）。
2. 合并用全角空格拼接，游戏内气泡是否需要换行未知（`/say` 只收 `text`）→ 如果显示难看，改成用「，」拼接。
3. `Date.now()` 足够（60s 窗口，钟跳概率可忽略）。

**已知取舍：**
- 3 秒内连发的同角色话会被合并成一句 → 「逐句」观感变化，仅限 spam 场景。
- `manual` 永不丢意味着极端情况下队列会超 20（有告警日志兜底）。
