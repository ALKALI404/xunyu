# 交接前 · 残留绑定检查（2026-10-27 立，血账换来的）

> **一句话**：归档一个还在链路上的会话 = 拆一段活线。
> 2026-10-26 那晚，前代 `df6c9f3e` 归档后仍有 **5 处活绑定**指着他，直接导致「QQ 能收不能发」——桥接把回复交给一个已经归档、不会再跑回合的会话去转述，对方只回「回合完成但无文本」，主人在 QQ 上一个字都收不到。

## 一、为什么会有这个文件

换代不是「建新会话 + 归档旧会话」两步就完事。这条链上至少 5 个地方记着「谁是主人会话」：

| # | 位置 | 作用 | 归档旧会话后不换会怎样 |
|---|---|---|---|
| 1 | `qq-bridge\state\sessions.json` | QQ 侧的会话映射（出站靠它） | **出站全断**：桥接叫醒一个死会话去转述，回复蒸发 |
| 2 | `avatar\state\owner-session.json` | 中继的默认主人会话 | 中继**每次重启都回弹**到旧会话，手动换绑白做 |
| 3 | 中继运行时 `targets.*`（`/health` 可查） | 窗口/QQ 两条线各绑哪个会话 | 归档后这两条线指向空，消息没人接 |
| 4 | DSH 定时任务（`~\.dsh\storages\schedule.json`） | 日课挂在哪个会话 | **归档直接被拒**：`workspace/session-active: active (schedule)` |
| 5 | `qq-bridge\config.json` 的 `dshShout.defaultTarget` / `watchSessions[]` | 默认喊话目标、主动关注列表 | 喊话打到空处；关注列表盯着一堆空壳会话刷日志 |

## 二、归档前必跑（一条命令）

```
cd E:\DSH_workspace
node scripts\scan-stale-bindings.mjs session-<旧id>        # 指定旧会话
node scripts\scan-stale-bindings.mjs                       # 或：自动取最近归档的 3 个 id
```

- 退出码 `0` = 只剩历史记录，可以归档；
- 退出码 `1` = **仍有活绑定，先修再归**；脚本会逐条给出文件、字段和修法。

## 三、手工兜底（脚本没覆盖到的）

1. **定时任务**：`schedule/list`（按 `sessionId` 查）→ 要保留的先在新会话重建、验 `state=scheduled`，再删旧的。实调用法：`schedule/delete {request:{sessionId, id}}`。
2. **中继**：`GET http://127.0.0.1:9334/health` 看 `targets.*.sessionId`；不对就 `POST /rebind {target:"xunyu"|"dsh", sessionId}`。
3. **中继回弹**：改完 `owner-session.json` **要重启中继**才生效（它启动时只读一次）。
4. **桥接映射**：`sessions.json` 里的 key 形如 `private:<QQ号>`、`group:<群号>`；改完同样要重启桥接。

## 四、顺序（照这个走，别倒）

```
准备换代
  → 旧会话的定时先迁/删（1、4 两项）
  → 新建会话 + 改名 + 换绑（3 项，POST /rebind 两条线）
  → 改 sessions.json / owner-session.json（1、2 项）
  → 重启中继 + 桥接，重跑扫描直到退出码 0
  → 最后才归档旧会话
```

> 反了会怎样：先归档 → 出站断、换绑回弹、归档被 schedule 拦，然后整晚在补洞。2026-10-26 就是这么过的。
