## 二、三条硬决策（本轮定死，后面只在必要时翻）

### 决策 1：**队列解耦**——工作台不直接碰企微客户端

- 工作台只做两件事：**读**（接入服务落库后的消息）与**写队列**（要发的消息 + 期望回执）；**绝不实时点击**；
- 助手端轮询队列 → 执行发送 → 写回执（`ok / code / detail`）→ 失败按类别退避，超过 N 次转"人工接管"；
- **为什么**：多客服并发点击会互相抢焦点；GUI 自动化天然慢且会失败；没有回执就无法回答"到底发出去没有"。
- **代价**：发送延迟（可接受 1–3 秒）、需要队列表与幂等键。

### 决策 2：**多租户目录隔离**——一套程序服务多个客户时，数据按目录隔开

- 每客户一个 `tenants\<租户id>\`（配置、数据库、日志、附件全在里面），**程序只认目录，不认全局状态**；
- 部署形态上：单客户就是 1 个租户目录；多客户 = 多个目录 + 一个总控（可选择不装总控）；
- **为什么**：买断 8000/套意味着客户可能自建、也可能我们代管；目录隔离让"拷走一个目录就能带走全部数据/换机"成立，也防止测试数据串到生产。
- **代价**：升级要按目录迁移（必须写迁移脚本 + 备份），不能"改一处全局生效"。

### 决策 3：**发送端可替换**——今天用客户端自动化，明天能换官方通道

- 发送端定义成接口：`send(target, payload) → {ok, code, detail, msgId}`，实现有三档：
  1. **客户端助手**（现在，已实测可送达）；
  2. **官方群发类接口**（限频，仅通知类场景可用）；
  3. **未来若有会话式 API**（直接替换实现，工作台不改）；
- 上层（工作台/队列）只依赖接口，**不许出现"Win32 点击"这种实现细节**；
- **为什么**：官方通道随时可能变（也可能放开）；把发送端做成可替换，是这套方案唯一能对抗"企微策略变更"的设计。
- **代价**：接口要多一层抽象，早期会显得绕。
