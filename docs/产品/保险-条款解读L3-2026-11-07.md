# 保险 · 条款解读 L3 架构规格（2026-11-07）

> **一句话**：把条款「**逐条翻成人话**」——每条给 **原文（一字不改）/ 人话（≤80 字）/ 边界（什么时候不适用）**，**不确定就标不确定**，**每条都能点回原文**；**不预测收益、不建议买不买**。
> 运行范围：**先做 L2 已配到条款的 7 张单**（单-0001、0005、0009、0011、0012、0016、0017），**不等 20 张全绿**。

## 二、解读粒度：条 → 段（沿用 L2 索引）

L2 的条款 JSON 已经是这个形状（实测样例 `档案\条款\240eeea92624667b.json`）：

```json
{ "no": "第二条", "title": "投保范围",
  "paras": [ { "i": 2, "text": "本合同接受的被保险人的投保年龄为出生满60天至70周岁1。", "page": 3 } ] }
```

L3 在**同一个 `para` 上**加三个字段（不改 L2 文件，另存解读文件）：

```json
{
  "source": "240eeea92624667b",
  "policyId": "单-0001",
  "generatedAt": "2026-11-07T02:10:00+08:00",
  "articles": [
    { "no": "第二条", "title": "投保范围",
      "paras": [
        { "i": 2, "page": 3,
          "text": "本合同接受的被保险人的投保年龄为出生满60天至70周岁1。",
          "plain": "这张单能保的人：出生满 60 天到 70 周岁；超出这个年龄不能作为被保险人。",
          "boundary": "年龄按投保时的周岁算；条款原文有脚注「1」，可能是年龄计算口径，需以保单记载为准。",
          "flags": ["ambiguous"]
        }
      ] }
  ]
}
```

**字段约束**：
- `text` **逐字取自 L2**（脚本 diff 必须为 0，改一个字都算失败）；
- `plain` **≤80 字**，说"这条对投保人意味着什么"，**不加原文没有的信息**；
- `boundary` 写**什么情况下不适用 / 常见误解**，至少一条；
- `flags` 见 §四；没有就空数组 `[]`。

## 三、三样内容的写法（硬规则）

| 字段 | 必须 | 禁止 |
|---|---|---|
| `text` 原文 | 与 L2 索引**逐字一致**；带 `page` 与条号 | 改写、合并段落、省略 |
| `plain` 人话 | 一句话说清后果；专业词（如"等待期"）用《保单词汇表》里的说法 | **加原文没有的数字/期限/条件**；写"建议您…"；写"划算/不划算" |
| `boundary` 边界 | 至少一条"什么时候不适用"或"最容易怎么误解" | 空话（"具体情况以条款为准"）；复制原文 |

## 四、不确定标注（三类，不许猜）

| flag | 什么时候用 | 页面上怎么显示 |
|---|---|---|
| `version-unconfirmed` | 条款版本/生效日期与保单对不上，或登记表里 `verifiedAt` 缺失 | 黄字「版本未确认，以保单为准」 |
| `ambiguous` | 原文本身有歧义（脚注、指代不明、"我们/您"混用） | 灰字「原文有歧义」+ 点开看原文 |
| `needs-insurer-confirm` | 需要保险公司口径才能回答（如"这个病算不算重疾"） | 蓝字「需向保险公司确认」，**不给答案** |

**规则**：flag 只标"不确定"，**不许用 flag 代替解读**（有 flag 也要给 plain/boundary）。

## 五、三条红线（写死）

1. **不做收益/赔付预测**：不写"到期能领多少""大概赔多少"，只转述条款写了什么；数字一律来自原文，原文没有就不写。
2. **不做"买不买"建议**：不出现"建议购买/不推荐/性价比"，**判断权在代理人（主人）**。
3. **每条解读必须能点回原文**：`plain`/`boundary` 旁边必须有「看原文」→ 跳到该条该段并高亮（页码来自 `page`）。

> 违反任一 → 该条不通过（见 §六判据 2/3）。

## 六、评测口径（怎么算"解读对"）

**三条判据**（每条解读都要过）：

| # | 判据 | 怎么判 | 反例（必须能拦） |
|---|---|---|---|
| 1 | **原文引用准确** | `text` 与 L2 索引 diff = 0（脚本） | 把"70 周岁"写成"70 岁"→ FAIL |
| 2 | **人话不含新信息** | 脚本抽 `plain` 里的数字/期限，逐个回原文找；找不到 → FAIL；人工再看措辞 | 原文只写"60 天"，人话出现"90 天等待期"→ FAIL |
| 3 | **边界说得对** | 人工核：至少一条可核对的不适用条件，且不空话 | "以条款为准"这种 → FAIL |

**抽样**：**每份条款抽 20% 的段**（最少 5 段），人工核；**判据 1 全量脚本跑**，判据 2 脚本预筛 + 抽样人工，判据 3 只人工。
**留痕**：抽样结果写 `档案\解读\评测\<hash>-<日期>.json`（抽了哪几段、谁判的、结论）。

## 七、失败处理（不许装懂）

| 情况 | 行为 |
|---|---|
| 条款没配上（13 张） | 页面「暂无本单条款（待补充）」+「去官网找」；**不生成解读** |
| 解析失败 / 条段结构坏 | **保留原文**（L2 文件在），解读字段 `null` + `flags:["parse-failed"]`，页面显示原文 +「解读暂缺」 |
| 模型给出原文没有的信息 | 判据 2 拦下，该段 `plain` 置 null 并标 `needs-regen`，**不展示错误解读** |

## 八、接口契约（给 04）

```http
GET /api/clause/explain?policyId=单-0001&no=第二条&para=2
  200 { policyId, source, no, para, page, text, plain, boundary, flags[], generatedAt }
  404 该单没有条款 / 该条段没有解读（body: {error:"no-explain", status:"no-clause|no-explain"})

POST /api/clause/explain/build        # 离线批处理（04 实现，页面不直接调）
  { source:"240eeea92624667b" | policyId:"单-0001", force?:false }
  202 { jobId, queued:true }          # 成功产出写 档案\解读\<source>.json
  404 条款不存在 ｜ 409 已在跑

GET /api/clause/explain/status?source=240eeea92624667b
  200 { source, status:"ok|building|failed|none", articles, paras, flagged, generatedAt }
```

**存储**：`档案\解读\<source>.json`（每份条款一个），**不覆盖 L2 的 `档案\条款\<source>.json`**。

## 十一、审实现后回写（2026-11-07 12:40｜05 审完 IN-040/041/042）

> 依据：`records\审稿\2026-11-07-05-审04-L3.md`。**本节优先于前文冲突处。**

### 11.1 示例 source 只示格式（P0 教训）

§二 的 `"source": "240eeea92624667b"` / `"policyId": "单-0001"` 是**格式示例，不是"拿这份跑"**。批处理的输入必须满足：

1. 是 `档案\条款\<hash>.json` 里**真实存在**的一份；
2. 该份的 `sourceName` 与保单 `product` **归一化后一致**（否则不挂、报 `needsReview`）。

**已发生的错**：单-0001（太平金生恒赢年金）被映射到 `240eee…`（太平**久久保意外伤害**），页面同屏出现「原文 30日–59周岁 / 人话 60天–70周岁」。修法见审稿 §一（A 止血 / B 归一 / C 硬门，C 必做）。

### 11.2 `needsReview` 是硬门，不是备注

`GET /api/clause/explain` 命中 `needsReview:true` 的映射时：**不返回 `plain`/`boundary`**（返回 `200 {plain:null, boundary:null, status:"unverified"}` 或 `409 {error:"unverified"}`），页面显示「解读待核实（产品名未对上）」，**不展示人话**。
理由：只把"待确认"放在 body 字段里，页面不会读它——这次就没人读。

### 11.3 flag 分两级（改 §四）

| 级别 | flag | 落点 | 页面 |
|---|---|---|---|
| **条款级** | `version-unconfirmed` | 解读文件顶层 `versionInfo: {declared, reason}` | 条款区**顶部一条横幅**「本条款版本未确认，以保单为准」 |
| **段级** | `ambiguous` / `needs-insurer-confirm` | 每个 `para.flags` | 段内标签 |

**禁止**对每段重复同一个条款级 flag（本次 246/246 段全标 → 等于没有信号）。

### 11.4 判据 2 口径（补 §六）

- 命中顺序写死：**本段 → 同一条 → 跨条不算命中**；跨条命中 = FAIL；
- 靠「同条兜底」通过的段，必须进评测留痕的 `weak[]`，人工抽样**优先看 weak**；
- 留痕新增 `weak[]` 与 `foundInArticle` 两个字段（本次 3 段）。

### 11.5 `status.flagged` 口径（补 §八）

- `flagged` = **不含 `version-unconfirmed`** 的段数；
- 另给 `flaggedBy: {ambiguous, needsInsurerConfirm, versionUnconfirmed}`，页面按 `flaggedBy` 分色，别各算各的。

### 11.6 L2 归一（新增前置票 IN-045；原误写 IN-044，那号已被微信适配占用）

- 现实是两套产物：`档案\条款\<hash>.json`（L3 吃）与 `窗口\clause-text\<policyId>.json`（页面读）；
- 定死：**hash 是主键，policyId 是外键**，同一份数据两个视图；`档案\条款\<hash>.json` 增 `policyIds[]`；
- **在归一见效前，L3 的可用面是 0 张单**（1 份无主条款 + 1 份错挂）——对外不要再写「7 张已有解读」。
