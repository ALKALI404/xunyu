# 规则 · 开源优先，别急着 vibe（2026-11-07 主人定）

> 主人原话：「以后能上 github 找开源件就先找来试试，如果确定不能用于大规模商用版本再自己 vibe」

---

## 一、默认顺序（不许跳步）

```
① 先找开源件（GitHub / npm / PyPI）
      ↓ 找到就 vendor 下来、跑通、改
② 开源件拿不到 / 许可证不行 / 实在不匹配
      ↓ 才允许自己写（vibe）
```

**"自己写"不是默认选项，是兜底选项。**

## 二、什么情况才算「不能用于大规模商用」（才允许自己写）

| 情况 | 判定 |
|---|---|
| **许可证是 GPL / AGPL / SSPL** | ❌ **不能用**（传染性，商用风险）→ 自己写 |
| **MIT / Apache-2.0 / BSD / ISC** | ✅ **可以用**（保留版权声明即可） |
| **无许可证（No license）** | ❌ **不能用**（法律上默认保留所有权利）→ 自己写或找替代 |
| **长期不维护（>18 个月无提交）** | ⚠️ **谨慎**：能用但要有替身方案 |
| **体积/依赖过重**（拖进来一个框架） | ⚠️ **只取模块，不搬全家** |
| **安全风险**（有已知 CVE、跑 ngrok 之类公网隧道） | ❌ **不用** |

## 三、操作要求（每项都要留证）

1. **记录来源**：仓库地址 + 版本/commit + 许可证 + 最后一次提交日期；
2. **vendor 到本地**：`vendor\<包名>\`（**不用 `npm install` 拉最新**，锁版本）；
3. **写清改了什么**：本地化、配色、去依赖——**改动集中在一个 patch 文件或注释块里**，方便以后升版；
4. **保留 LICENSE 原文**（MIT 也要求）；
5. **能省多少代码**：写一句估计（对照自己写要多少行）。

## 四、优先级顺序（找的时候按这个看）

1. **MIT/Apache 的成熟库**（Star 高、最近半年有提交）；
2. **同一作者的小而专的库**（比大框架好改）；
3. **我们自己已经 vendor 过的**（`vendor\` 里先翻一遍，别重复找）；
4. **只借鉴思路不搬代码**（最后手段，等于自己写）。

## 五、谁来执行

| 角色 | 职责 |
|---|---|
| **05 文档与架构** | **选型调研**：找候选、核许可证、核维护状态、出选型报告、**拆实现票** |
| **04 代码** | 按票 vendor + 改 + 接 |
| **06 界面** | 按票改样式（复用件优先） |
| **本体** | 验收时查：**"这个为什么不直接用现成的？"**（没答案就打回） |

## 六、验收时怎么查（本体/01 用）

- **新增业务代码 > 300 行** 且**没做过开源调研** → **打回**，要求先出选型报告；
- **引入 GPL/AGPL** → **一律不通过**；
- **vendor 目录里没有 LICENSE** → **打回**；
- **说"找不到"但没写搜过哪些关键词** → **打回**（**找不到也要留证据**）。

## 七、一句话记法

> **能抄就抄（合法的抄），不能抄再写；写之前先说清"为什么不能抄"。**
