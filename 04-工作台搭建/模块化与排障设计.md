> 目标（主人原话）：**大部分功能改成「功能接口对接功能模块」；以后查问题简化成——哪个模块异常、是接口问题还是模块问题、链路哪一段断。**

## 0. 结论先说

现在的代码**文件级已经分了，接口级几乎没有**：
- 好消息：40 个 src 文件职责清楚（`sticker-lib` `forward` `pending-prompts` `token-alert` 各自导出干净函数），`body-service` 甚至已经是「能力接口」的样子（`/say` `/anim` `/emotion` `/health` `/capabilities`）。
- 坏消息：**没有契约、没有 trace、没有统一 health**，所有东西靠 `bridge.js`（12,726 行）内部直接调用函数，跨进程只有裸 HTTP/裸 RPC。所以出问题时只能「读代码 + 猜」。

**改法不是「重写成微服务」，而是三件小事：给接口加信封、给模块加 manifest、给链路加 traceId。** 有了这三样，排障就从「猜」变成「查表」。

## 2. 现状评估：模块化成色

| 维度 | 现状 | 差在哪 |
|---|---|---|
| 文件分区 | ★★★★ | 40 个文件职责清楚 |
| 函数导出 | ★★★☆ | 多数模块导出纯函数，可直接被调 |
| 接口契约 | ★☆ | 没有 schema / 错误码 / 超时约定；`/api/*` 五十多个端点风格不一 |
| 跨进程可观测 | ★ | 没有 traceId，日志按文件散落 |
| 健康/自检 | ★★ | body 有 `/health` `/capabilities`，bridge 只有 `/api/status`，企微只有 `/health`，DSH 没有 |
| 编排（谁先起、谁守） | ★★ | supervisor + watchdog + 计划任务三层，规则不一致 |

**一句话**：**已经有「模块」，缺的是「接口」和「链路」。**

**实测补记（今晚验的）**：`9334/health`、`9335/health`、`9335/capabilities`、`8788/health` 都是 200 且返回结构化 JSON；**只有 `3100/api/status` 要 `x-console-token`，401**——也就是说**命门（桥接）是唯一没有公开探针的模块**。这条本身就是「统一 health 协议」的第一个理由。

## 3. 目标形态：功能接口 + 功能模块

### 3.1 接口信封（所有跨模块调用统一）

```json
// 请求
{ "traceId": "t-7f3a", "cap": "qq.send.text", "caller": "wake@3100",
  "args": { "target": "group:<群A>", "text": "…" },
  "deadlineMs": 15000, "retry": { "max": 2, "backoff": "exp" } }

// 响应（成功）
{ "traceId": "t-7f3a", "ok": true, "data": { "messageId": "…" }, "elapsedMs": 812 }

// 响应（失败）——错误码必须能定位到层
{ "traceId": "t-7f3a", "ok": false,
  "error": { "layer": "contract|module|transport", "code": "timeout|bad-args|down|not-ready",
             "module": "qq-adapter", "detail": "OneBot 200 但 messageId 空" } }
```

**`layer` 是关键**：查问题时第一眼就知道是**接口对不上**（contract）、**模块坏了**（module）、还是**网络/进程不通**（transport）。

### 3.2 模块标准（每个功能模块 = 一个目录 + 一个 manifest）

```
modules/<name>/
  manifest.json  {
    name, version, kind: service|tool|adapter|plugin,
    entry, ports: [3100], health: "GET /health",
    capabilities: ["qq.send.text", "qq.send.sticker", ...],
    configSchema, dependsOn: ["store", "dsh-rpc"], owner
  }
  index.mjs      // 只导出 start/stop/health/handle(cap, args)
  README.md
```

宿主（一个 `host` 进程）只做四件事：**按 dependsOn 排序启动 / 统一探活 / 统一重启退避 / 汇总 capabilities**。现在这些散在 `supervisor.ps1`、`watchdog.ps1`、`start.bat`、bridge 自己里。

### 3.3 链路 trace（一行一跳）

每个跨模块调用写一行到 `logs\trace.jsonl`：

```json
{ "t": 1793123456789, "trace": "t-7f3a", "from": "qq-adapter", "to": "wake",
  "cap": "wake.decide", "in": 128, "out": 3, "ms": 12, "ok": true }
```

**排障时不用读代码**：`grep t-7f3a trace.jsonl` 就能看到整条链在哪一跳变红（`ok:false` 或 `ms` 超阈值）。

## 4. 五个可判定检查点（把故障变成表格题）

| # | 检查点 | 判定 | 对应今天的真事 |
|---|---|---|---|
| 1 | 适配器活着吗 | `/health` + 端口 listen | 企微 8788 被 job 杀掉 |
| 2 | 入站事件进了吗 | 适配器 `ingress.count` 递增 | 群消息「被吞」先看这里 |
| 3 | 唤醒判定了吗 | `wake.decide` 有 trace 且 out>0 | 概率改不动 = 配置来源不一致 |
| 4 | 投递到会话了吗 | `dsh.prompt` 返回 accepted + 30s 内对端回合 | 04 B 单六小时零回执 |
| 5 | 出站送达了吗 | `recordOutboundHistory` 有 messageId | 「已收集」≠「已送达」 |

**今天三次事故按这套表，全部是 5 分钟内可定位的**：
- 企微被杀：检查点 1（`/health` 挂）→ 直接看守护；
- 群消息被吞：检查点 3/4（有 decide、无 accepted）→ 落在投递；
- 唤醒配置被覆盖：检查点 3 + **「配置只有一个写入口」**（现在是文件/API 两份）；
- 我说「她没有收款码」：不属于链路，属于**查询面不全** → 见 §6 的「能力发现」问题。

## 6. 顺带补一条：能力发现（我今天栽的那一跤）

我查「她有没有收款码」时翻了磁盘、memory、聊天记录，**没想到收藏表情也是一个存储**——结果答错。

**结构性解法**：每个模块在 manifest 里声明 `stores: [...]`（我存什么、存在哪），`host` 汇总成一张「全系统存储地图」。以后问「有没有 X」，先查地图，而不是靠我记得哪里存过东西。

## 8. 落地顺序（改订 2026-10-28 凌晨，主人拍板）

**原则：`bridge.js` 是上游下载来的模块，我们只是魔改——它排最后，且在动它之前必须先把「外围」做干净。**

| 阶段 | 做什么 | 碰 bridge.js 吗 | 风险 |
|---|---|---|---|
| ① 今天可做 | 给**我们自己的**模块加统一 `health/capabilities` + trace：`body-service`(9335)、`relay`(9334)、企微 `server.mjs`(8788)、`scripts\*` 命令行工具 | **不碰** | 极低 |
| ② 只读不改 | 给 3100 加一个**外挂探针**（另起一个 50 行的小进程，探 `/api/status` 带 token 后转成公开 `/health`），bridge 本体不动 | 不碰（外挂） | 低 |
| ③ 摸清上游 | 给 bridge 建「魔改清单」：改了哪些文件、哪些函数、对应下载版哪一行；同时冻结一份原始副本作 diff 基线 | **只看不改** | 零 |
| ④ 小手术 | 只做**纯增量**改动：加 `/capabilities` + 写 trace 的 3 个调用点；不改任何既有分支 | 碰（只加） | 中 |
| ⑤ 抽 outbound / wake | 把已有函数搬到独立文件、bridge 里只留转发（行为不变，一次只搬一个） | 碰（搬家） | 中高 |
| ⑥ store 收敛 | 四个写手并成一个（最脏的一块） | 碰 | 高 |
| ⑦ 删守护 / 统一调度 | 合并 `watchdog.ps1` 与 `supervisor.ps1` | 碰 | 中 |

**不做的事**：不重写、不换技术栈、不一次性拆 12,726 行。每次只搬一个能力，搬完立刻用 §4 的检查点验一遍。

## 9. 改「上游魔改模块」的守则（明天照这个来）

1. **先有基线，才动手**：动手前 `copy` 一份 `bridge.js` 到 `backup\bridge-<日期>.js`，并记下 sha256 + 行数。没有基线的改动等于以后无法 diff。
2. **魔改清单先行**：维护一张 `state\bridge-魔改清单.md`，一行一处：`文件 / 函数名 / 行号 / 改了什么 / 为什么 / 下载版对应位置`。**上游升级时照这张表重放补丁**，不然一升级全丢。
3. **只加不删**：第一轮只允许「新增函数、新增路由、新增日志」，不允许改既有分支逻辑。要改逻辑，先加开关（`cfg.experimental.*`，默认关）。
4. **一次一个改动 + 一次实测**：改完立刻用五个检查点验（适配器活 / 入站 / 唤醒 / 投递 / 送达），验不过就回滚到基线。
5. **可回滚**：每次改动留 `backup\` 副本；重启由 supervisor 负责，**手动 kill 要记时间**，事后对照它是否自愈。
6. **魔改的边界写进文档**：哪些文件是「我们的」、哪些是「上游的」，README 里列清楚——现在 `src/` 里两者混在一起，谁也不敢删。
